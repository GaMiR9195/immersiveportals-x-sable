# Разбор: «капли» в оверлее, проваливание на скорости, странные сессии

Этот документ — результат перечитывания четырёх файлов целиком:
`IplEnteringVolumeVisualization`, `IplAtlasStraddleSession`, `IplStraddleSessionSync`,
`PortalCrossingDetector`, `SableTransitController`. Ни один из двух больших файлов здесь
не перезаписан целиком намеренно: правки — четыре крошечных ханка, и переписывание 77k и
42k символов вслепую, без компиляции, рискует сломать уже проверенный билд сильнее, чем
стоит любая из этих правок. Ханки приведены дословно, применяются за минуту.

## 1. «Капли» — это артефакт оверлея, а не баг

Зелёная «точка A» рисуется из `PortalCrossingDetector.bufferedPose(...)`, а он отдаёт, в
этом порядке:

1. живой `EXIT_ANCHORS` (буферизованный выход),
2. иначе `trail.older` — если `hasOlder`,
3. иначе `trail.start` — если сегмент засеян выходом,
4. иначе `null`, и тогда оверлей падает на `ship.lastPose()`.

В обычном падении без порталов работает пункт 2, а `trail.older` — это поза **двухтиковой
давности** (`captureTrail` делает `older.set(start)` перед `start.set(lastPose())`). Значит
расстояние от зелёного до тела равно пути, пройденному за два тика. Под гравитацией этот
путь растёт каждый тик — поэтому зелёное «поднимается всё выше и выше» над падающим телом,
и тем быстрее, чем быстрее тело. Когда разгон прекращается, разрыв перестаёт расти и
зелёное «останавливается», а затем идёт вниз вместе с голубым (`lastPose`, один тик
давности) — ровно то, что ты описал, включая «дёргаясь». Телепорт вниз — это тик, в котором
сегмент был засеян якорем выхода: точка A мгновенно становится створом портала.

То есть скорость «капанья» — это визуализированное **ускорение**. И вот почему момент, когда
капанье визуально останавливается, совпал с проваливанием: капанье перестаёт расти, когда
путь за тик выходит на постоянную величину, а проваливание срабатывает именно по порогу
«путь за тик», см. §2. Оверлей не врал — он показывал сам порог.

`captureTick` вызывается в контроллере ДО `captureTrail`, так что оверлей всегда отстаёт ещё
на тик. Это тоже нормально для дебага, но при чтении картинки это надо держать в голове.

## 2. Проваливание на скорости: у `withinExitClearance` нет теста направления

В детекторе два соседних охранника, и они не симметричны:

- `entryWithinExitSlab(...)` — сначала `backwardTravelIntoPlate(...) <= EPSILON → false`,
  то есть движение ВПЕРЁД никогда не отказывается. Правильно.
- `withinExitClearance(...)` — только `latch.overlaps(currentBounds(...))` и
  `plateIsRectangleOf(...)`. Никакого направления. Достаточно **находиться** на плите.

Теперь геометрия. `armExitClearance` строит плиту как **destination**-прямоугольник
(`exitFrame.mapPoint(portal.getOriginPos())`). В петле из двух порталов destination-
прямоугольник портала A — это, геометрически, прямоугольник портала B, то есть ровно та
дверь, которой телу нужно воспользоваться следующей. `plateIsRectangleOf` сравнивает по
`Math.abs(dot)`, значит матчит и B, и её обратную грань.

Следствие в контроллере:

```java
if (!haveSession
    && (PortalCrossingDetector.entryWithinExitSlab(airship, state.entryTime())
        || PortalCrossingDetector.withinExitClearance(airship, portal)
        || (twin != null
            && PortalCrossingDetector.withinExitClearance(airship, twin)))) {
    continue;
}
```

Тело, которое успевает добраться до парного портала за `EXIT_LATCH_MAX_TICKS = 3` тика,
получает `continue` — молча. Кандидат не создаётся, rehome не происходит, тело проходит
плоскость насквозь и падает дальше. Это **чистый порог по скорости**:

> путь за тик ≳ (расстояние между порталами петли) / EXIT_LATCH_MAX_TICKS

Поэтому «около 150+ пролетает насквозь», а на меньшем импульсе — нет. И поэтому 5 TPS
никогда не помогали: порог в блоках за тик, а не в секундах.

Это тот же самый провал, который описан в комментарии `armExitClearance` про плиту на
входной грани («следующее, совершенно легитимное пересечение A отказывалось каждый раз»).
Перенос плиты на destination не убрал баг, а перенёс его с A на B.

**Ханк 1** — `PortalCrossingDetector.withinExitClearance`, сразу после
`if (!latch.overlaps(currentBounds(airship))) return false;`:

```java
        // ДВИЖЕНИЕ ВПЕРЁД НЕ ЕСТЬ «ВСЁ ЕЩЁ ВЫХОЖУ».
        // Позиция не отличает «выхожу» от «возвращаюсь»: и то и другое происходит на
        // одном прямоугольнике. Отличает направление — и именно оно определяет вход с
        // обратной стороны. Без этого теста плита на destination-прямоугольнике отказывает
        // парному порталу петли, что и есть порог «путь за тик >= расстояние/latchTicks».
        if (IplTransitGuards.DIRECTIONAL_EXIT_CLEARANCE
            && backwardTravelIntoPlate(airship, latch) <= EPSILON) {
            return false;
        }
```

## 3. Сессии: `plateIsRectangleOf` не может совпасть со входной гранью

`armExitClearance` кладёт латч под UUID портала, в который тело **влетело**, а плиту строит
из прямоугольника, из которого тело **вылетело**. `plateIsRectangleOf` сравнивает
`portal.getOriginPos()` с `latch.ox/oy/oz`, то есть с *отображённым* origin. Для входной
грани эти точки отличаются на всю изометрию портала → тест ложный **по построению**.

Значит `touchesPortalVirtually(body, entranceFace)` после транзита всегда `false`. А
сессии кеются на входной грани (`StraddleKey(shipUuid, portalUuid)` для входного портала),
и ветка exit-гистерезиса в контроллере спрашивает именно про входную грань:

```java
if (PortalCrossingDetector.touchesPortalVirtually(airship, portal)) {
    seenHostedKeys.add(key);
    IplAtlasStraddleSession.onStraddleTick(airship, portal, normal);
    continue;
}
IplAtlasStraddleSession.clear(key, reason);
```

То есть вся ветка — мёртвый код: сессия либо снимается на следующем тике после того, как
была построена, либо доживает до постороннего reap. Ровно это и видно как «sweep странно
работает с сессией на медленном проносе»: beam Creative Physics Staff маршрутизируется
через отображение сессии, а сессия уже не согласна с телом. В 0.5.0 этой ветки не было
вовсе, поэтому и «похожего не было» — сравнивать надо не sweep, а именно жизненный цикл.

**Ханк 2** — `PortalCrossingDetector.plateIsRectangleOf`, сразу после `if (portal == null) return false;`:

```java
        // Латч зарегистрирован под UUID ВХОДНОГО портала, а плита — это прямоугольник
        // ВЫХОДА. Геометрический тест ниже поэтому никогда не отвечает за входную грань,
        // и touchesPortalVirtually(body, entrance) всегда ложь — то есть ветка
        // exit-гистерезиса в SableTransitController мёртвая. Идентичность должна
        // покрывать оба конца двери.
        if (IplTransitGuards.LATCH_MATCHES_ENTRANCE
            && latch.portalId != null && latch.portalId.equals(portal.getUUID())) {
            return true;
        }
```

Важно: ханк 2 сам по себе усиливает отказы в §2 (входная грань теперь тоже матчится), так
что **ханк 1 и ханк 2 применяются вместе**. С направленным тестом отказ остаётся только для
реального возврата в дверь.

## 4. Ханк 3 — латч становится настраиваемым

```java
    private static final long EXIT_LATCH_MAX_TICKS = IplTransitGuards.EXIT_LATCH_MAX_TICKS;
```

Дефолт тот же (3), поведение не меняется. Смысл в том, что теперь `3` и направленность
бисектятся вместе: комментарий в детекторе верно отмечает, что 40 тиков вдвое сокращали
выживание петли — но это следствие §2, а не свойство длинной плиты. С направленным тестом
длинная плита ничего не стоит.

## 5. Ханк 4 — отказ перестаёт быть молчаливым

В логе за 20 секунд нет ни одной строки `[IPL-IMAGE] start/end` и ни одной
`[IPL-TRANSIT]`, при том что `580ca223` за пять секунд уходит с y=-182.2 на y=-267.0 при
`portal=no-session`. То есть тело в свободном падении мимо петли, и ни одна сессия за это
окно не открывалась и не закрывалась. Это подпись именно молчаливого `continue`, а не
недетекта: детектор бы ничего не залогировал в обоих случаях, и различить их по текущему
логу невозможно. Поэтому:

```java
                    if (!haveSession) {
                        String refused = null;
                        if (PortalCrossingDetector.entryWithinExitSlab(airship, state.entryTime())) {
                            refused = "entry-within-exit-slab";
                        } else if (PortalCrossingDetector.withinExitClearance(airship, portal)) {
                            refused = "within-exit-clearance";
                        } else if (twin != null
                            && PortalCrossingDetector.withinExitClearance(airship, twin)) {
                            refused = "within-exit-clearance-twin";
                        }
                        if (refused != null) {
                            IplTransitGuards.refusedCrossing(airship.getUniqueId(), portalUuid,
                                refused, PortalCrossingDetector.segmentLength(airship));
                            continue;
                        }
                    }
```

Это дословная замена блока из §2, семантика та же (короткое замыкание в том же порядке),
плюс имя охранника и `travel/tick` в логе. `travel/tick` печатается специально: порог из §2
сформулирован ровно в этих единицах, так что строка сразу показывает, попало ли тело в него.

По желанию — `IplTransitGuards.clear()` в `SableTransitController.onServerStopping` рядом с
`PortalCrossingDetector.clearTrails()`.

## 6. Что этим НЕ починено

- **Один флип на тело за тик.** Контроллер это фиксирует явно
  (`flippedThisTick`, `candidateAddedForAirship = true; break;`), и это не баг, а
  архитектурное ограничение: детекция читает сегмент, который физика уже произвела, так что
  внутри одного тика тело нельзя телепортировать и переобнаружить. Цепочка дверей проходится
  по одной за тик, и это работает благодаря буферу выхода. Но если после флипа тело
  оказывается уже ЗА второй дверью, а §2 отказывает ей три тика — оно уходит наружу петли.
  То есть §2 надо править первым; итеративное разрешение нескольких пересечений за тик — это
  отдельная, крупная работа по контроллеру, и её нельзя делать без компиляции.
- **Причина именно «20 секунд».** По коду это не выводится: 20 с при 20 TPS — 400 тиков, а
  ни один из констант-таймеров (`EXIT_LATCH_MAX_TICKS=3`, `ACTOR_RESYNC_INTERVAL=100`,
  `WINDOW_MAX_AGE_MS=5000`, `HANDOFF_FORCE_MS=1000`) на 400 тиков не ложится. Скорее всего
  это не таймер, а момент, когда разгон тела дотягивает `travel/tick` до порога §2 — что и
  совпадает с «капанье остановилось». Новая строка `[IPL-TRANSIT-GUARD]` это подтвердит или
  опровергнет за один прогон: если в момент бага она печатается с
  `guard=within-exit-clearance`, гипотеза верна.
- **Ничего из §2-§5 не скомпилировано.** Ханки маленькие и локальные, но билд после них надо
  прогнать.
