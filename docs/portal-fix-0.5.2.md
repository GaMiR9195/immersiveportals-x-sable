# 0.5.2 — переходы Sable через порталы

Это новая редакция исходников после замечаний к предыдущему варианту. Версия форка в
`gradle.properties` — **0.5.2**; upstream `mod_version=6.0.7` сохранён отдельно.
Архив содержит исходники, не готовую проверенную игровую сборку.

## Что было изучено в Sable и companion

Проверялась не только геометрия в моде:

- Sable 2.0.3: `SubLevelPhysicsSystem`, `SubLevelTrackingSystem`, серверный и клиентский
  контейнеры, `ClientSubLevel`, `ClientSableInterpolationState`,
  `SubLevelSnapshotInterpolator`, movement/info/start/stop-tracking packets.
- Companion: представление `Pose3d`/`Pose3dc`, rotation point, преобразование координат,
  копирование и интерполяция pose. Координаты plot не являются координатами мира.
- Simulated: создание клиентского захвата, серверный `drag`, orientation и жизненный цикл
  motor constraint; модовые grab-chain, RPC, beam/axis и визуальный pick.
- В моде: fused physics step, occupied-block sweep, Atlas session/image/clip lifecycle,
  parent flip, residual loop, клиентские snapshots/session store, source clipping,
  projections и вложенные render-pass. Сверена Rust-семантика clip regions и joint walk.

## 1. Почему возникало «подвисание → догоняющий рывок»

Sable хранит snapshots с tracking tick и читает их по **отстающему** указателю.
При handoff предыдущий вариант удалял весь буфер и вставлял две точки около самого
нового tick. Если указатель ещё раньше первой оставшейся точки, `getSampleAt()`
возвращает эту первую точку. Это пауза до догоняющего движения указателя, а не
необходимая остановка физического тела. Повторение в loop создаёт периодический рывок.

В 0.5.2 при смене координат преобразуются:

1. Каждый buffered snapshot, с его **исходным tick**.
2. `runningSnapshot` интерполятора.
3. `lastPose` и `logicalPose`, независимо друг от друга.
4. Render-pose cache и границы обоих конечных положений.

Буфер не очищается, фиктивные ticks не добавляются, clock/delay/stopped state не
перезапускаются. Для портальной изометрии `P` сохраняется
`P(interpolate(A,B,t)) = interpolate(P(A),P(B),t)`. Поэтому смена координат сама по себе
не должна менять фазу движения.

## 2. Какая именно snapshot находится в какой системе координат

Серверный transit вызывается в TAIL контейнера **после tracking observer**.
Tracking уже отправил source snapshot с tick `k` и увеличил свой счётчик. Handoff
фиксирует значение этого счётчика: `firstDestinationTick = k + 1`.

До применения отложенного клиентского handoff новые destination snapshots приводятся
обратно к видимой source-системе, но только если их tick достиг соответствующей
границы. Snapshot старше границы уже source-frame — повторно обращать его нельзя.
Несколько переходов обращаются в обратном порядке; применяются затем FIFO в прямом.
Несколько переходов в одном server tick могут иметь одинаковую временную границу.

Для hosted snapshots принудительно сохраняется ordered TCP, включая случай игрока
в hosting dimension. Их обработка не смешивается с обгоняющим UDP-потоком.

Handoff больше не требует заново доказать серверный переход по независимому клиентскому
sweep. Он применяется, когда старые render endpoints вышли либо задержанная временная
шкала достигла server completion. Учтён stopped clock с большим interpolation delay.
Отсутствие render sample или несинхронизированный portal entity не может навсегда
запереть подтверждённый переход.

## 3. Почему dimension id недостаточно и откуда мог появиться сдвиг на портал

Проход A→B внутри одного dimension тоже меняет координатный кадр. Поэтому введён
монотонный номер **coordinate frame** на sub-level, отдельный от dimension и tick.
Он передаётся в handoff, session snapshots и parent bootstrap/restamp.

Клиент не применяет future-frame session к ещё source-frame pose. Последнее полное
состояние будущего кадра ждёт своей FIFO-смены координат. Старые сообщения кадра
игнорируются; при переключении не переносятся source-frame clip/tail в новый кадр.
Parent stamp не обгоняет очередь handoff. Свежий destination full-sync не преобразуется
повторно как будто это старое source тело.

Это устраняет конкретные пути смешивания видимой и физической систем координат.
Это **не утверждение**, что редкий описанный баг воспроизведён и доказанно исчез в игре.

## 4. Конечный прямоугольник, withdrawal и нормальный выход

Настоящий A→B sweep использует continuous SAT occupied-block OBB против конечной
портальной пластины. Для чистого переноса это непрерывный тест; вращение разбивается
на участки с ограничением ошибки дуги. Фаза APPROACHING/STRADDLING/CROSSED не подменяет
само геометрическое пересечение. Lateral aperture margin приведён к **0**, а не
полблока за рамкой; normal hysteresis остаётся отдельным условием удержания.

Одного факта «раньше вошёл» недостаточно для завершения. Добавлена проверка конечного
контакта последней source-геометрии с прямоугольником при выходе через нулевую плоскость.
Если объект сначала просунули, потом вывели вбок и лишь затем провели через продолжение
плоскости, такой участок не считается завершением через портал.

Выход на нулевой плоскости запоминается отдельно: он может произойти раньше достижения
0.1 phase hysteresis. При возврате source-геометрии этот completion отзывается.
Новая обычная straddle session требует текущего конечного контакта, а не только
контакта в давно покинутой части текущего sweep.

## 5. Почему нельзя просто выключить все полностью прошедшие изображения

У rigid joint-группы ведущий sub-level может уже выйти, пока хвостовой ещё проходит.
У ведущего нет текущего пересечения с пластиной, но есть **история настоящего конечного
выхода**. Такое completed-состояние передаётся клиенту и сохраняет destination image
до атомарного переключения всей группы. Это не право любого объекта удерживать
бесконечную плоскость: состояние привязано к конкретному входу и coordinate frame.

Группа preflight-проверяется до первого перемещения; её члены получают одну изометрию
до следующего native solver step. В residual loop не запускаются дополнительные physics
steps и не добавляется время. На следующий портал идёт остаток траектории после
завершения, а не отрезок между координатами до и после телепортации.

В существующем native API rigid-группа — ship-to-ship joints с angular locks
(fixed/revolute/prismatic в соответствующей конфигурации). Ball/spring/rope-соединения
не превращены в rigid assembly; для ropes сохранён отдельный seam path.

## 6. Визуальная сессия больше не живёт только по знаку полупространства

Retired tail имеет server end tick и существует только до достижения этого момента
отстающей render timeline. Для частичного split также проверяется конечный OBB–plate
контакт, для обычных visual predictions — lateral bounds и ограниченный grace period.
Исторически completed joint member рассматривается отдельно, как описано выше.

После смены frame удаляются старые retired/source-session состояния. При удалении
client object и выходе из мира очищаются очереди, активные/retired/handoff visual states,
frame records, render samples и состояние Staff. Surrogate с прежним UUID перестраивается,
если изменились NBT или dimension, а не навечно хранит старую геометрию.

Предыдущая render pose теперь одинакова во всех вложенных portal passes одного кадра.
Первый проход больше не видит A→B, пока следующий ошибочно видит B→B.

## 7. Creative Physics Staff

Server motor/orientation и visual pose намеренно имеют разные временные шкалы.
Визуальный beam использует цепочку, приведённую к delayed client frame; команды
вращения остаются в authoritative server frame. Завершённый, но ещё видимый split
берётся из того же render-session состояния, что и изображение конструкции.

Новый grab сообщает, на каком coordinate frame сделан pick. Если сервер уже совершил
переходы после этого кадра, seed дополняется **записанными серверными** изометриями,
а не угаданной текущей позицией портала. Для этого сохраняется ограниченная история
body transits. За пределами истории pick отклоняется с завершением захвата, а не
привязывается к неверному телу.

Каждый повторный grab имеет новый seed ID. Старые rebase/clear/ack предыдущего захвата
того же UUID не могут повернуть или очистить новую сессию. Повторный rebase одной
ревизии не поворачивает orientation второй раз.

## Совместимость и что действительно проверено

- Изменён внутренний Java RPC протокол: клиент и сервер должны быть **оба 0.5.2**.
- Native ABI/Rust solver не изменены. Нужна совместимая patched Atlas DLL; в исходном
  архиве её не было, поэтому в новом ZIP она не выдумана и не подменена stock native.
- Поддержка остаётся scale-1 isometry; произвольные scaled/custom-shaped portals этим
  исправлением не заявляются. Бюджет residual обработки — 16 переходов за один tick.
- У существующего Staff grab-chain остаётся лимит 32 ссылок; бесконечно длинный held
  route этим патчем не превращён в доказанно поддерживаемый случай.
- Java мода и resources скомпилированы с реальными зависимостями. Использован сохранённый
  mapped NeoForge/Minecraft artifact; повторная декомпиляция всего Minecraft упёрлась
  в память окружения. Успешная компиляция не доказывает отсутствие игрового jitter.
- Сделаны небольшие целевые проверки finite trailing exit, бокового выхода и разделения
  нулевой плоскости/phase hysteresis; имеющиеся detector fixtures также проходят.
- Minecraft с вашей сборкой/native DLL здесь не запускался. Loop, rotated portals,
  joint-группы, быстрые withdrawal/re-grab и поведение при задержке сети требуют проверки
  именно в игре. Гарантии «катастрофически стабильно» без неё было бы нечестно давать.
