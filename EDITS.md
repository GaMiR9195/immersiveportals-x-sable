# Ревизия 9

Отменяет две мои собственные ошибки и закрывает интерполяцию. Причина «сессия не закрывается / нет rehome» найдена в коде, а не угадана, и это была регрессия ревизии 8.

## 0. Чего я не понял в прошлый раз

`PORTAL_HYSTERESIS_DEPTH = 0.1` тут ни при чём, и вы это сразу сказали. Проверено по `Frame`:

```java
Vec3 x = pose.transformPosition(new Vec3(1,0,0)).subtract(origin);
double obbSupport(double x, double y, double z) {
    return (|xx·x+xy·y+xz·z| + |yx·x+yy·y+yz·z| + |zx·x+zy·y+zz·z|) * 0.5;
}
```

Базис строится на **единичных** векторах плота, значит `obbSupport` — половина габарита **одного кубика**, а не всего тела. Поэтому `min >= 0.1` в `phase()` означает «каждый блок ушёл за плоскость на десятую долю блока». Пронести рукой этого достаточно, порог rehome не блокирует.

## 1. Настоящая причина отсутствия rehome (регрессия ревизии 8)

Гейт кандидата без живой сессии требовал `startedBeforePortalPlane()`, то есть чтобы `trail.start` лежал **позади** плоскости этого портала. А в ревизии 8 я, по вашему же алгоритму, засеял трейл выходным якорем: `older = start = anchor`, `hasOlder = false`, где якорь стоит на 0.01 **за** покинутым прямоугольником (`reseedTrailFromExitAnchor`, ветка `MONOLITHIC REHOME` в `captureTrail`).

В loop выходной прямоугольник портала A геометрически совпадает с прямоугольником портала B. Значит относительно **B** сегмент начинается уже за плоскостью, `startedBeforePortalPlane` = false, кандидат не строится, **rehome через B невозможен вообще**, а сессия портала A остаётся висеть. Это ровно то, что вы описывали: сессия не закрывается, и проход сквозь плоскость ничего не даёт.

До ревизии 8 `older` ставился *перед* швом, поэтому rehome работал — и тем же самым изготавливал вход с обратной стороны. Я обменял один баг на другой.

Исправление в `SableTransitController`: для сегмента, засеянного выходом, требование позы позади плоскости снято, остальное не тронуто.

```java
boolean startedSourceSide = state.startedBeforePortalPlane()
    || PortalCrossingDetector.hasBufferedExit(airship);
```

Доказательство настоящего прохода при этом остаётся полным без него: `sweptIntersectsPortalAperture()` — конечное пересечение именно этой апертуры, `sweptEntryDirection()` — знаковое направление источник→назначение. Требование «поза позади плоскости» поверх этого только переспрашивает, где случайно разрезан сегмент.

## 2. Сессия закрывается состоянием тела, а не событием одного тика

Две независимые поломки:

* `ipl$settleExit` вызывался **только** из цикла исполнения кандидатов, то есть исключительно на тике флипа. А `PortalCrossingDetector.settleExit()` на этом тике возвращает `null`, пока тело перекрывает плиту — что на тике флипа всегда так. Второго вызова не существовало, поэтому выход, не завершённый в тот самый момент, не доводился до конца никогда.
* Ветка закрытия в скане была закрыта `withinExitClearance()`, который после ревизии 7 стал чистой проверкой тождества прямоугольника и отвечает «да» всё время жизни защёлки. Тело давно вне полосы, а портал всё ещё «его».

Теперь `ipl$settleExit(level, airship)` вызывается один раз за тик сразу после `captureTrail`, а решение принимает единый предикат контакта:

```java
if (PortalCrossingDetector.touchesPortalVirtually(airship, portal)) { ... re-tick ... }
```

`touchesPortalVirtually` — это тождество плиты **и** геометрическое перекрытие, то есть буквально «касается ли sub-level портала с учётом 0.01 виртуального утолщения его плоскости». Как только ответ «нет», выход настоящий, и сессия снимается сразу, а не по исчерпании бюджета тиков. Это тот самый прямоугольник вместо plane, и это тот же ответ, которым обязаны пользоваться все потребители, включая Creative Physics Staff, — плоскость портала при этом не двигается ни на что.

## 3. Интерполяция: от выхода до точки rehome

Механизм подтверждён по оригинальному sable, `SubLevelSnapshotInterpolator`:

* `getSampleAt` делает `before.pose.lerp(after.pose, factor, dest)`;
* `tick(backTick)` держит 6 тиков истории и **каждый тик пересчитывает** `runningSnapshot`;
* `receiveSnapshot` хранит позу **по ссылке**.

На флипе в буфере лежат старые снапшоты в **исходном** кадре, а новые уже приходят в **кадре назначения**, и `backTick` идёт позади. Несколько тиков лерп идёт между кадрами — тело рисуется пролетающим **всю дистанцию между связанными порталами**, повторно. Это и есть мельтешение по всему переходу. И это объясняет, почему мои разовые записи в `runningSnapshot` не жили дольше тика.

Исправление в `applyHandoff`: история старше пересечения принадлежит несуществующему кадру, поэтому она **отбрасывается** — не отображается через портал (ревизия 5 и раньше: история уезжала на высоту loop) и не сворачивается в одну точку (ревизия 6: движение пропадало). Вместо неё сажаются ровно два конца выхода:

```java
synchronized (interpolator.buffer) {
    exitTick = interpolator.buffer.isEmpty() ? Integer.MIN_VALUE
        : interpolator.buffer.getLast().gameTick();
    interpolator.buffer.clear();
}
interpolator.receiveSnapshot(exitTick,     new Pose3d(exitPose));
interpolator.receiveSnapshot(exitTick + 1, new Pose3d(mappedLogicalPose));
```

После этого `getSampleAt` нечего интерполировать, кроме «плоскость выхода → точка rehome». Копии поз обязательны, потому что буфер хранит ссылки.

Миксин для этого не понадобился: `buffer` — публичное поле, `Snapshot` — `public record`, а `IplPendingHandoffSnapshotMixin` уже держит приходящие снапшоты в исходном кадре до применения handoff, так что двойного отображения нет. Вмешательство в буфер при этом легально по правилам самого sable: `splitFrom()` точно так же переписывает прошлые снапшоты в новый кадр через `madeUpPastPose` и пересортировывает буфер. Прошлое нужно делать **правильным**, а не стирать.

Исчезновение, которое эта хирургия однажды вызвала, теперь структурно невозможно: доказательство пересечения — `FORWARD_SWEEPS`, и `clearPredictionKeepingProof()` его сохраняет, поэтому `hasForwardApertureSweep()` больше не обязан выводить исходную сторону из буфера, который законно находится на стороне назначения.

Порталы это не задевает: трейл детектора пересобирается отдельно, через выходной якорь, и в буфер интерполятора sweep detect не смотрит. При обратном выходе handoff не происходит вовсе, значит и посева нет — протаскивать нечего.

Серверная сторона уже владеет тем же отрезком: `executeHostedTransit` делает `updateLastPose()`, затем `previousPose = projectOntoExitPlane(...)`, а `logicalPose` — точка rehome. По проводу это гнать не нужно: клиент выводит идентичный конец через `projectOntoExitPlane` из уже присланного портального преобразования.

## Файлы

* `transit/SableTransitController.java` — гейт `startedSourceSide`, `settleExit` каждый тик, закрытие сессии по `touchesPortalVirtually`
* `client/IplParentDimSync.java` — посев отрезка выхода в таймлайн интерполятора

Rapier не тронут: `PhysicsPipeline.teleport` / `RigidBodyHandle.teleport` дёргаются только самим rehome, а протаскивание выхода теперь чисто визуальное и не идёт через физический телепорт.

# Ревизия 8

Три моих собственных ошибки исправлены. Все три были попытками угадать вместо чтения кода.

## 0. Откат буквального сдвига плоскости (моя ошибка ревизии 7)

`planeOriginFor()` физически смещал `portal.getOriginPos()` на 0.01 вдоль направления выхода и
подставлял результат во все проверки `evaluate()` (`sample` x2, `sweepSegment` x2) и в
`willEnterAperture()`.

Это неверно. 0.01 — **виртуальное** удлинение, правило о том, что ещё считается нахождением в
двери, а не геометрический офсет портала. Сдвиг плоскости меняет ответ для тел, не имеющих к этой
двери отношения, и для граней, которые никто не пересекал.

Удалено. `evaluate()` и `sweepSegment()` снова измеряют от `portal.getOriginPos()`, сигнатура
`sweepSegment` вернулась к семи параметрам без `planeOrigin`, `willEnterAperture` — к обычной
плоскости. Осталось от ревизии 7 только то, что действительно чинило loop: `EXIT_LATCH_MAX_TICKS = 3`
и геометрическое ограничение защёлки одним прямоугольником (`plateIsRectangleOf`).

## 1. Защита от входа с обратной стороны — настоящая причина

Алгоритм, который требовался: зашёл → сессия открыта → закрыть её можно либо выйдя на 0.01 дальше,
либо вернувшись назад; **точка прошлого заменяется текущим положением**, которое уже на 0.01 дальше
плоскости; при развороте sweep-детектор видит разницу 0.01 и прохода через заднюю грань не находит.

В коде это было реализовано **только** в `reseedTrailFromExitAnchor()` (путь settle):
`older = start = anchor`, `hasOlder = false`.

А в `rebaseTrailThroughPortal()` (путь самого rehome) было сделано **наоборот**:

```java
double entryT = ... crossingTime ...;
Pose3d prior = StraddleMapping.of(portal).mapPose(
    interpolate(trail.start, trail.end, Math.max(0.0, entryT - 1.0e-3)));
trail.older.set(prior);
trail.hasOlder = true;
trail.start.set(armExitAnchor(airship, portal, entry));
```

Поза берётся **до шва** и протягивается через портал. До пересечения тело ещё не доехало до входа,
поэтому её образ ложится **позади выходного прямоугольника**. На любой реальной скорости сегмент
длиной несколько блоков, так что `entryT - 1.0e-3` — это уверенно за плоскостью.

Дальше `evaluate()`:

* `oldest = sample(older)` → `startedBeforePortalPlane = oldest.minDistance < -EPSILON` → **true**;
* `historic = sweepSegment(older -> start)` → пересечение плоскости в сторону назначения → **TOWARD_DESTINATION**.

Трейл **сам изготавливал** доказательство свежего входа через совмещённую заднюю грань, на каждом
rehome. Именно поэтому добавление 0.01 к выходу никогда не помогало: 0.01 висел на `start`, а `older`
был намеренно поставлен за плоскость.

Исправлено: точка прошлого заменяется текущей, то есть якорем.

```java
Pose3d anchor = armExitAnchor(airship, portal, entry);
trail.older.set(anchor);
trail.start.set(anchor);
trail.hasOlder = false;
```

Теперь разворот даёт развёртку **из точки за плоскостью обратно к ней** — детектор видит разницу
0.01, классифицирует `TOWARD_SOURCE`, и прохода через заднюю сторону просто не существует. Точки
позади плоскости больше нет ни для мельтешения, ни для экстраполяции, ни для шума float.

Информация о направлении не потеряна: она берётся из сегмента, который реально произошёл в этом
кадре — `anchor -> текущая поза`, честное движение наружу через ту грань, из которой тело вышло.
Оба пути (`rebase` и `reseed`) теперь согласованы, а не противоречат друг другу.

## 2. Виртуальное удлинение как вопрос о контакте

`exitPlaneThickness()` (возвращал 0.01/0.0) заменён на `touchesPortalVirtually(airship, portal)` —
один общий ответ на «это sub-level ещё в этом портале?». Пока тело выходит, оно **считается
касающимся** двери, даже если геометрически уже вышло, — до тех пор, пока не прошло 0.01. Ничего в
прямоугольнике портала при этом не двигается.

Это правило обязано быть общим для всех sub-level: сессия держится через эту полосу, и потребитель,
решивший что тело уже не касается портала, расходится с сессией и обрабатывает тело как вышедшее.
Это и есть артефакт Creative Physics Staff на «практически вышедшем» теле.

**Не доделано:** `IplStraddleStaffPick`, `IplGrabChainClient`, `IplStaffBeamRoutes`,
`PhysicsStaffSubLevelObserver` пока не вызывают `touchesPortalVirtually`. Авторитет есть, потребители
не перевязаны.

## 3. Интерполяция: почему она не работала вообще и почему тело исчезало

Моя правка ревизии 6 в `applyHandoff()` не «не сработала» — она **уничтожала данные**, на которых
держится визуальный переход.

`IplClientVisualTransitLatch` не переключает визуальный кадр, пока клиент не докажет, что тело
прошло сквозь конечную апертуру вперёд. Доказательство — либо `FORWARD_SWEEPS`, записанное на
подлёте, либо, если его нет, вывод заново через `hasBufferedForwardSweep()` / `crossesAperture()`.
Оба резервных пути требуют начальную позу **целиком с исходной стороны**: `from.maxPlane() < -EPSILON`.

Что делала моя правка:

1. `IplClientVisualTransitLatch.clear(subLevelId)` в первой строке `applyHandoff` — а `clear()`
   делает `FORWARD_SWEEPS.remove(shipId)`, то есть **стирал доказательство**;
2. перезапись всего буфера в `exitPose` / `mappedLogicalPose` и `lastPose = exitPose` — все позы
   оказывались **на плоскости или за ней**.

Итог: `recorded == null`, `crossesAperture` ложна для каждой пары, `hasForwardApertureSweep()`
возвращает false, визуальный хвост снимается. Тело исчезает вместо вылета, и игрок видит обычное
серверное падение без выхода из портала — ровно то, что было сообщено.

Вторая, независимая причина: интерполятор авторитетен каждый тик. `tick(backTick)` пересчитывает
`runningSnapshot` из буфера через `getSampleAt()`. Закрепление этого поля жило ровно один тик.
Позы, записанные на клиенте, не могут пережить следующий снапшот.

Исправлено:

* хирургия буфера и закрепление `runningSnapshot` удалены;
* добавлен `clearPredictionKeepingProof()` — снимает устаревшее предсказание, но **сохраняет**
  `FORWARD_SWEEPS`; пересечение действительно состоялось, доказательство остаётся;
* `lastPose = exitPose` оставлен: это то, что заставляет `renderPose()` тянуть
  «дверь -> точка rehome» внутри самого кадра флипа, и это зеркалит сервер.

### Где настоящее решение

Сервер **уже** владеет правильным ответом. `SableRehomeOps.executeHostedTransit()`:

```java
hosted.updateLastPose();                                   // сворачивает lastPose на logicalPose
Pose3d exitPlanePose = PortalCrossingDetector.projectOntoExitPlane(hosted, portal, mappedPose);
((IplSubLevelPreviousPoseAccessor) hosted).ipl$getPreviousPose().set(exitPlanePose);
```

То есть серверный вектор `lastPose -> logicalPose` буквально равен «плоскость портала -> точка
rehome». Но эта конечная точка **не передаётся**: поток снапшотов несёт только `logicalPose`.

Правильный фикс — отправить `exitPlanePose` в RPC хэндоффа (`sendParentHandoff` сейчас несёт
`uuid, dimLocation, transform, portalNbt`). Тогда клиент ничего не синтезирует и не угадывает: он
ставит `lastPose` из авторитетной позы, идентичной серверной. Это изменение провода, оно не сделано
в этой ревизии.

  `exitPlaneThickness` → `touchesPortalVirtually`; точка прошлого в `rebaseTrailThroughPortal`

### Правка 1. Кривой portal cut с треугольным разрезом у одноблочных sub-level

#### Что не так было

У Sable **две** vanilla-ветки рендера sub-level, и они несовместимы по пространству вершин:

| | `VanillaChunkedSubLevelRenderData.renderChunkedSubLevel` | `VanillaSingleSubLevelRenderData.renderSingleBlock` |
|---|---|---|
| Что в атрибуте `Position` | **plot-local**, относительно камеры (`Position + ChunkOffset`) | **eye space** — `modelView * transform` запечён в вершины на CPU |
| Где живёт поворот sub-level | в `MODEL_VIEW_MATRIX`, загружается уже после вершин | внутри самих вершин (`stack.last().pose().mul(modelView).mul(transform)`, затем `tesselateBlock`) |
| Как рисуется | по секциям, свой draw на sub-level | **все** одноблочные sub-level склеиваются в ОДИН `Tesselator`-меш и сливаются позже из `renderAfterSections` |

Весь портальный клиппинг мода висел **только на чанковой ветке**:

* `SableSourceClipMixin` — `@Mixin(VanillaChunkedSubLevelRenderData)`, инжекты в `renderChunkedSubLevel` HEAD/RETURN;
* `SubLevelClipUniformPatcher.patchPortalClipForVanillaSubLevel` пересчитывает уравнение IP из slot 0 (`iportal_ClippingEquation`) именно во входное пространство **этой** ветки;
* `grep -rn 'VanillaSingle' src/main/java/ipl/sable` → **ни одной ссылки**.

Отсюда ровно то, что видно в игре. Для одноблочного тела уравнение IP, построенное в camera-relative **WORLD** пространстве, скалярно умножалось на **EYE**-позицию вершины. А eye space — это `R_view * p_world`, и

```
n_world · (R_view · p) == (R_view^T · n_world) · p
```

то есть эффективная нормаль реза оказывалась **повёрнутой на обратный поворот камеры**. Плоскость под неправильным косым углом, режущая один куб, — это в точности **треугольный угловой разрез**, и его площадь менялась при каждом повороте/смещении камеры. Ровно симптом из отчёта: «разрез кривой, треугольный, видимость и размер зависят от положения камеры относительно портала».

Вторая половина: собственный рез мода (slots 1/2, `gl_ClipDistance[1]`/`[2]`) для этой ветки **не устанавливался вообще** — разделения source/destination у одноблочных не было в принципе.

#### Почему НЕ стали писать клип для одноблочной ветки

Рассматривался вариант «сделать второй клип-кронштейн поверх `renderSingleBlock`». Отклонён:

1. Одноблочная ветка батчит **все** одноблочные sub-level в один общий `BufferBuilder`, и слив идёт одним `layer.draw(meshData)`. Одна плоскость на draw порезала бы и те тела, что рядом с порталом даже не стоят. Пришлось бы разбивать батч Sable по sub-level.
2. Переписывание `renderAfterSections` требует приватных внутренностей Sable (`singleBlockLayers`, `setupDynamicEffects`) и не проверяется компиляцией на нашей стороне.

#### Что сделано

Hosted-тела уводятся на чанковую ветку, которая уже режется правильно.

Новый миксин `ipl/sable/mixin/client/IplHostedSingleBlockChunkRenderMixin.java`: инжект в HEAD `VanillaSubLevelRenderDispatcher.isSingleBlock(ClientSubLevel)`, и если `IplDimAgnostic.isHosted(subLevel)` — `cir.setReturnValue(false)`.

Почему это не хак, а поддерживаемая конфигурация Sable: `isSingleBlock` **сам** возвращает false для любого блока с тегом `SableTags.ALWAYS_CHUNK_RENDERING`. То есть чанковый рендер плота 1x1x1 — путь, который Sable держит намеренно. Мы принимаем то же решение, только по признаку «это наше тело», а не по тегу блока.

Важно, что решение **стабильно на всё время жизни** sub-level (hosted не меняется), поэтому проверка переаллокации в `resize()`

```java
renderData instanceof VanillaSingleSubLevelRenderData ^ isSingleBlock(subLevel)
```

не начнёт дёргаться. Вариант «уводить на чанки только пока тело страддлит портал» здесь был бы катастрофой: в loop-е это переаллокация render data **каждый тик**.

Побочный выигрыш: одноблочная ветка — это же та ветка, где тела раньше пропадали целиком (она зависит от отдельного слива `renderAfterSections` и от непустого `singleBlockLayers`). Hosted-тела от неё больше не зависят, старый частный костыль на невидимость больше не нужен.

#### Изменённые файлы

* `src/main/java/ipl/sable/mixin/client/IplHostedSingleBlockChunkRenderMixin.java` — новый
* `src/main/resources/ipl_sable.mixins.json` — регистрация в массиве `client`

#### Проверка

* Пронести **одноблочный** sub-level через портал: рез должен совпадать с плоскостью портала и **не** реагировать на движение камеры.
* Покрутить камерой вокруг портала — форма реза неподвижна.
* Многоблочные тела не должны измениться (их путь не тронут).
* В логах ожидается `[IPL-CLIP-PATCH]` / `SourceClipDiag.onVanillaCall` и для одноблочных тел тоже — раньше их там не было.

### Правка 2. Не видно интерполяции выхода из портала до точки rehome

#### Что не так было

`IplParentDimSync.applyHandoff` прогонял через портальную изометрию **всю** историю интерполятора:

```java
synchronized (interpolator.buffer) {
    for (int i = 0; i < interpolator.buffer.size(); i++) {
        Snapshot s = interpolator.buffer.get(i);
        interpolator.buffer.set(i, new Snapshot(s.gameTick(), mapping.mapPose(new Pose3d(s.pose()))));
    }
}
```

Два следствия, и вместе они и есть баг:

1. **История — это то, ОТКУДА `renderPose()` интерполирует.** Перенеся её, мы переносим и саму интерполяцию: тело не «выныривает» из портала, оно всегда было по ту сторону. Это буквально «интерполяция телепортируется вместе с sub-level». В вертикальном loop-е (портал сверху + портал снизу) образ пред-переходной позы лежит **позади** выходного прямоугольника, а «позади нижнего портала» — это **над** потолком. Отсюда «она может оказываться сверху».
2. **Операция не идемпотентна.** Если пакет движения за тик флипа попал в буфер **раньше** этого RPC, он уже в destination-кадре — и его отобразят **второй раз**. Это ровно одна лишняя высота loop-а на один кадр (в логах: `Δ −0.954`, затем `Δ −10.955`; `Δ −0.810`, затем `Δ −10.812` — избыток 10.00 = высота loop-а). Тика-штампа, чтобы отличить один случай от другого, здесь нет, а при rehome каждый тик эта гонка — не редкость, а норма.

При этом `mappedLastPose` сам по себе стартовой точкой быть не может — до перехода тело ещё **не дошло** до входа, значит его образ лежит позади выхода.

#### Что сделано

Таймлайн больше **не отображается через портал** — он **пересаживается на дверной проём**.

1. **Начало отрезка.** Новый метод на записи `PortalMapping`:

   ```java
   Pose3d projectOntoExitPlane(ClientSubLevel sub, Pose3d destinationPose)
   ```

   Толкает позу вперёд по направлению контента портала, пока **задняя** кромка тела не лягнет на выходной прямоугольник + `EXIT_PLANE_CLEARANCE = 0.01` (то самое +0.01, что на сервере). Если тело уже за плоскостью — не трогает.

   Клиентское зеркало серверного `PortalCrossingDetector.projectOntoExitPlane`: одна поза, один кадр, одно отображение. Меряются **восемь углов плота** (`bounds.minX()` … `bounds.maxX() + 1.0`), а **не** `Pose3d.position()` — position это образ plot-local `(0,0,0)`, то есть **угол** плота, а не тело; притягивание его к плоскости сдвинуло бы весь объём на метры (эта ошибка уже была и уже откатывалась, см. ранние ревизии).

2. **Конец отрезка** — `mappedLogicalPose`, куда фактически поставил rehome.

3. **Сама пересадка.** Выход должен читаться как «тело пролетело сквозь проём»: оно **было у проёма**, оно **теперь в точке rehome». Поэтому вся историческая часть буфера сворачивается в `exitPose`, а самый свежий снапшот (по `max gameTick`) несёт `mappedLogicalPose`:

   ```java
   int newest = argmax(gameTick);
   buffer.set(i, new Snapshot(s.gameTick(), new Pose3d(i == newest ? mappedLogicalPose : exitPose)));
   ```

   Интерполятор после этого выдаёт **ровно «портал → точка rehome»**, непрерывно, на любой скорости.

4. **Идемпотентность.** Ни один снапшот больше не прогоняется через `mapPose`, поэтому двойное отображение из пункта 2 «Что не так было» **исчезает как класс** — фильтр по тикам не нужен. История — неподвижная точка этой перезаписи, так что повтор каждый тик в loop-е её не сдвинет. Это прямой ответ на «каждый тик делается проверка и сразу rehome, это не должно ломать её».

5. **Что видит игрок в тик флипа.** `runningSnapshot` ставится в `exitPose` (следующий же кадр показывает тело **у портала**, а не рывок в точку rehome), а `lastPose` — тоже в `exitPose` вместо прежнего `mappedLastPose`. `renderPose(pt)` лерпит `lastPose → logicalPose`, значит внутри самого тика флипа проигрывается отрезок **проём → точка rehome**. На больших скоростях это и есть тот отрезок, который раньше не было видно.

Про экстраполяцию, которую вы подозревали: она реальна — `SubLevelSnapshotInterpolator.getSampleAt` при наличии только `before` делает dead-reckoning на **один** тик через `beforeBefore` (`dest.set(beforeBefore.pose).lerp(before.pose, 1.0 + fraction)`). Но вела себя «глупо» она не сама по себе: ей подсовывали историю, отображённую через портал, и она честно экстраполировала **из неправильного места**. С пересаженным на проём таймлайном экстраполировать больше не из чего — `beforeBefore` и `before` теперь оба на проёме.

#### Изменённые файлы

* `src/main/java/ipl/sable/client/IplParentDimSync.java`
  * константа `EXIT_PLANE_CLEARANCE = 0.01`
  * `PortalMapping.projectOntoExitPlane(ClientSubLevel, Pose3d)` — новый
  * `applyHandoff` — переписана работа с таймлайном

#### Проверка

* **Loop (портал сверху + портал снизу):** тело должно падать ровно **от верхнего до нижнего портала**, без появления над потолком и без рывка. Это главный тест.
* На большой скорости отрезок «портал → точка rehome» должен быть **видимым**, а не мгновенным.
* Оставить тело в loop-е на минуту: дрейфа вверх/вниз быть не должно (проверка идемпотентности при rehome каждый тик).
* В логах `[IPL-PARENT-SYNC] handoff applied for ... pose=(...)` — pose должна быть точкой rehome, а не точкой на высоту loop-а выше.

### Правка 3. Вход с обратной стороны портала при мельтешении (несмотря на +0.01)

#### Что не так было

Три независимых дефекта, и +0.01 не мог помочь ни против одного.

**Дефект A — предикаты уничтожали защиту сами.** `withinExitClearance` и `entryWithinExitSlab` — **предикаты**, но оба делали `EXIT_LATCHES.remove(id)` внутри себя. Транзитный скан спрашивает их про **каждый** портал-кандидат в тике, и отдельно про **совмещённого двойника** каждого портала. Первый же портал, который с площадкой не пересекается, стирал площадку — и все порталы, рассмотренные в этом тике **позже**, оставались без защиты. А тот портал, который надо защищать, — это как раз тот, из которого только что вышли, и он в списке далеко не первый. У самого `withinExitClearance` в комментарии написано «This method is a PREDICATE. It must not mutate the trail» — и тут же мутация карты защёлок.

**Дефект B — проверка личности по UUID не могла совпасть никогда.** `armExitClearance` кладёт защёлку под UUID портала, **в который** тело влетело, а площадку строит на прямоугольнике, **из которого** вылетело:

```java
EXIT_LATCHES.put(airship.getUniqueId(), new ExitLatch(portal.getUUID(), origin…, normal…, …));
```

Значит `latch.portalId.equals(portal.getUUID())` в `withinExitClearance` не мог быть истинным ни для портала на площадке, ни для его совмещённого двойника. Метод отвечал «нет, это чужой выход» **про единственный портал, который он существует чтобы защищать**.

**Дефект C — потолок 3 тика.** `EXIT_LATCH_MAX_TICKS = 3L`. Через три тика площадка исчезала, и тело, всё ещё мельтешащее у проёма, спокойно входило с обратной стороны. Три тика — это заметно меньше, чем человек мельтешит рукой. Поднять потолок было нельзя: площадка отказывала **любому** входу внутри себя, включая законное следующее прямое пересечение, поэтому долгая площадка убивала loop.

**Дефект D — NaN.** `boundsAt(airship, t)` приводит нефинитный `t` к `0.0`, а `state.entryTime()` на нескольких путях `evaluate` равен NaN. Для разворота начало отрезка — это **дальняя** сторона площадки, то есть NaN-вход проходил сквозь защиту молча.

#### Что сделано

1. **Предикаты стали чистыми.** Новый read-only доступ `liveExitLatch(ServerSubLevel)`; обе `EXIT_LATCHES.remove(id)` из обоих предикатов убраны. Право снимать защёлку осталось только у `settleExit` (геометрическое освобождение + пересев тропы) и у `beginTrailTick`.
2. **Срок годности — один раз за тик,** в `beginTrailTick`: `EXIT_LATCHES.values().removeIf(l -> trailTick - l.tick > EXIT_LATCH_MAX_TICKS)`. Порядок обхода порталов внутри тика больше ни на что не влияет.
3. **Личность — геометрическая, не по UUID.** Проверка `latch.portalId.equals(...)` убрана; пересечение с площадкой **и есть** проверка личности — площадка это и есть прямоугольник того самого портала, раздутый на 0.01. `portalId` оставлен только для диагностики и для возврата из `settleExit`.
4. **Защита стала НАПРАВЛЕННОЙ** — это ключ ко всему. Позиция принципиально не различает «выхожу» и «возвращаюсь»: и то и то происходит на одном прямоугольнике. Различает **направление**, и именно оно и определяет вход с обратной стороны:

   ```java
   if (backwardTravelIntoPlate(airship, latch) <= EPSILON) return false;
   ```

   `backwardTravelIntoPlate` берёт смещение центра тела по удержанному отрезку (`boundsAt(airship, 0.0)` → `currentBounds(airship)`) и проецирует на нормаль площадки. Нормаль портала смотрит в ту сторону, **откуда** входят, поэтому `+n` — это «назад в проём». Отказ только при движении назад в проём; кто ещё вылетает — законно завершает пересечение.
5. **Потолок поднят 3 → 40 тиков** (2 с) — теперь это можно, потому что прямые пересечения площадка больше не блокирует вообще, сколько бы она ни жила. Быстрый loop (всегда вперёд) не получает отказов, а площадка переживает целую серию мельтешения. Штатное освобождение осталось геометрическим, в `settleExit`, как только текущая поза перестала касаться площадки; 40 тиков — только страховка на случай тела, припаркованного внутри полосы 0.01.
6. **NaN обезврежен:** вход без пригодного времени проверяется по текущей позе, а не пропускается:

   ```java
   return !Double.isFinite(entryTime) && latch.overlaps(currentBounds(airship));
   ```

Конструкция самой площадки в `armExitClearance` не тронута — она правильная (`StraddleMapping.of(portal)`, затем `mapPoint(portal.getOriginPos())`, `mapVec` для нормали и осей, полуразмеры из `getWidth()/getHeight() * 0.5`, `clearance = max(EXIT_CLEARANCE_THICKNESS, MIN_EXIT_CLEARANCE)`).

#### Изменённые файлы

* `src/main/java/ipl/sable/transit/PortalCrossingDetector.java`
  * `EXIT_LATCH_MAX_TICKS` 3 → 40, с обоснованием
  * `beginTrailTick` — срок годности защёлок
  * `liveExitLatch`, `backwardTravelIntoPlate` — новые
  * `withinExitClearance` — чистый предикат, геометрическая личность
  * `entryWithinExitSlab` — чистый предикат, направленная проверка, обработка NaN

#### Проверка

* **Главный тест:** мельтешить вплотную к порталу (вперёд-назад, серией) — вход с обратной стороны не должен происходить ни разу, в том числе дольше 3 тиков подряд.
* Loop на скорости не должен стать медленнее или начать «пропускать» проёмы: прямые пересечения не отказываются.
* Тело, припаркованное ровно в проёме, должно освободить защёлку не позже 40 тиков.
* Многопортальная цепочка (порталы в 0.02 блока друг от друга) — вход в следующий портал должен приниматься сразу.
* Логи: `[IPL-TRANSIT]` / `[IPL-FLIP]` — не должно быть пар флипов A→B→A на нулевом пройденном расстоянии.

## 2026-08-15 — Монолитный rehome: буфер «фейковой точки A» на выходном портале

### Что не так было

Rehome не переносит тело на выходную рамку — он мапит **весь физический сегмент**
через портал, поэтому тело законно оказывается дальше выходной рамки (игрок видит
это как интерполяцию, и это правда: постройка там действительно была, просто это
не попало на границу тика).

При большой скорости «дальше рамки» = **за следующим порталом**. И тут ломалось:

1. `SableTransitController.onContainerTick` → `SableRehomeOps.executeHostedTransit`
   → `PortalCrossingDetector.rebaseTrailThroughPortal` — корректно строит сегмент
   после шва (`start` = мапнутая поза входа, `older` = поза чуть до шва, `end` =
   текущая поза).
2. Дальше в том же проходе вызывался `ipl$settleExit` → `settleExit(...)`. Если тело
   уже вышло за 0.01-слой (а быстрое тело выходит **всегда**), сессия закрывалась и
   вызывался `resetTrail(...)`, который **схлопывал `older`/`start`/`end` в одну
   текущую позу** — то есть уничтожал единственное доказательство, что тело в этом
   тике вылетело из апертуры.
3. На следующем тике `captureTrail` видел `rebasedThisTick` и делал
   `trail.start.set(trail.end)` — новый сегмент начинался там, где тело **уже
   находится**. Если это «уже» было за следующим порталом — сегмент A→B ни разу не
   пересекал его апертуру. Портал пропускался, тело проваливалось сквозь него.

### Что сделано

Rehome и sweep detect сшиты в одну операцию через **буфер выходной позы**
(«фейковая точка A»). Существующая рабочая логика не переписывалась — добавлено
недостающее звено истории.

#### `transit/PortalCrossingDetector.java`

- **Новое состояние `EXIT_ANCHORS`** (`Map<UUID, ExitAnchor>`) + класс `ExitAnchor`
  (`pose`, `portalId`, `tick`) рядом с `ExitLatch`.
  - Константы: `EXIT_ANCHOR_OFFSET = 0.01`, `EXIT_ANCHOR_MAX_TICKS = 1`.
  - Якорь живёт **ровно до следующего тика** — до сегмента, который его потребит.

- **`armExitAnchor(airship, portal, sourceCrossingPose, mappedCrossingPose)`** — новый
  метод, ставит буфер. Правила размещения:
  - **Относительно того, как выходит именно это тело.** Берётся собственная поза
    пересечения тела, пронесённая через портал. Не центр портала, не рамка по граням.
    Два тела, выходящие через разные углы одной двери, получат разные якоря — только
    так следующий sweep остаётся коллинеарен реальному движению.
  - **Корректно для порталов разного размера.** Позиция считается через
    `portal.transformPoint(...)`, то есть через собственный трансформ портала, который
    несёт и поворот, и `scaling`. `StraddleMapping` намеренно остаётся scale-1
    (сессии гейтят масштаб), и при `scaling == 1` оба пути дают ровно один и тот же
    результат — сегодня это все порталы. Логика изменения размера sub-level не
    требуется: точка уже понимается относительно размеров прямоугольника.
  - **Сдвиг только по направлению выхода.** `+0.01` вдоль
    `Portal.getContentDirection()` — это направление выхода контента в целевом кадре.
    Грани плоскости не раздуваются (никакого ободка `|→`), ровно как у бэнда
    удержания сессии. Якорь не может оказаться на волосок **позади** выходной грани
    (иначе он читался бы как заход через совпадающую заднюю грань) и не может
    вылезти вбок из проёма.

- **`rebaseTrailThroughPortal(...)`** — теперь ставит якорь и стартует хвост с него:
  - поза пересечения в **исходном** кадре (`sourceEntry`) захватывается **до**
    пересоздания трейла, иначе повторный маппинг унёс бы якорь на целый трансформ
    портала;
  - `trail.start` = якорь (а не «голая» мапнутая поза пересечения);
  - `trail.older` (история направления через шов) и `armExitClearance(...)` —
    без изменений, как и работало.

- **`settleExit(...)`** — больше **не** схлопывает трейл. Вместо `resetTrail(...)`
  вызывается новый `reseedTrailFromExitAnchor(...)`, который делает сегмент
  `выходная апертура → текущая поза` и **оставляет якорь** для следующего захвата.
  Сессия закрывается ровно как раньше — теряется только потеря истории.
  Если живого якоря нет (обычный выход со стороны источника), поведение прежнее —
  fallback на `resetTrail(...)`.

- **`captureTrail(...)`** — если предыдущий тик закончился флипом (`rebasedThisTick`)
  **и** якорь жив, новый сегмент начинается с якоря, а не с `trail.end`. Якорь тут же
  потребляется (`EXIT_ANCHORS.remove`). Именно это даёт: тело, материализовавшееся за
  следующим порталом, **этим же тиком** имеет сегмент «выходная апертура → текущая
  поза», который штатно пересекает апертуру следующего портала и открывает переход.
  Никаких спец-случаев для «второго портала» в коде нет — работает обычный A→B sweep.

- **Служебное:** `forgetTrail`, `resetTrail`, `clearTrails` чистят якоря;
  добавлены `bufferedExitAnchor(...)` / `bufferedExitAnchorPortal(...)` для отладки
  (по аналогии с `bufferedPose`); приватный `liveAnchor(id)` с проверкой возраста.

#### `transit/SableTransitController.java`

- Комментарий блока EXIT SETTLEMENT переписан под новое поведение (re-seed из
  буфера вместо схлопывания в текущую позу).
- Javadoc `ipl$settleExit` — то же самое.
- Над циклом исполнения кандидатов добавлено явное описание реальной модели:
  **один флип на тело за тик, но каждый тик целиком** — детект по свёрнутому
  сегменту, флип родителя, буферизация выходной позы, settlement сессии.

### Вырезано (мусорная галлюцинация)

Убраны утверждения о «цепочке пересечений внутри одного тика» / «обнаружение и
телепортация за один тик». Это невозможно: детект читает сегмент, который физика
**уже** посчитала, поэтому нельзя телепортировать и тут же заново задетектить внутри
того же тика.

Заменено на честную формулировку: каждый тик выполняется полный цикл
(детект → телепорт → начало rehome → буфер), а непрерывность между тиками
обеспечивает буфер выходной позы. Цепочка порталов проходится по одному порталу за
тик, без разрывов и пропусков, при любой скорости.

Конкретные места:
- `PortalCrossingDetector.java` — комментарий про историю направления через шов;
  комментарий-предикат в `withinExitClearance`; разбор портального цикла
  («16 бесполезных флипов за тик» / «per-tick budget» → «тик за тиком флип при
  нулевом пройденном пути»); шапка `armExitClearance`.
- `SableTransitController.java` — комментарий у запроса порталов («может пересечь
  портал за тик» → «внутри одного физического сегмента»); шапка цикла кандидатов.

### Не трогалось

`armExitClearance` / `withinExitClearance` / `entryWithinExitSlab`,
`ipl$ownsCoincidentFace`, исключение по dual-parity, гарантии по задней грани,
логика сессий, `SableRehomeOps.executeHostedTransit`, атомарный перенос rigid-мейтов,
rope/grab re-seam. Всё это работает и оставлено как есть.

## 2026-08-15 (правка 2) — регрессия 12.5 с → ~6 с: цикл тратил 2 тика вместо 1

### Симптом

После первой правки время выживания в лупе упало примерно вдвое. Это ровно то, что даёт
потеря каждого второго тика: скорость, при которой луп ещё держится, тоже падает вдвое.

### Что реально происходило (найдено перечитыванием кода, не догадкой)

**1. Главная причина — `resetTrail` + `break` в контроллере убивали буфер и весь тик.**

В `SableTransitController.onContainerTick`, в ветке `else` (`reason` = `backed-out` /
`left-aperture`) при живой сессии выполнялось:

```java
IplAtlasStraddleSession.clear(key, reason);
IplEnteringVolumeVisualization.replaceBuffer(airship);
PortalCrossingDetector.resetTrail(airship);   // а resetTrail удалял EXIT_ANCHORS
break;                                        // и бросал весь перебор порталов
```

Цепочка запуска: в тик перелёта `settleExit` возвращает `null`, пока тело ещё пересекает
только что выставленную пластину (`if (!expired && latch.overlaps(currentBounds(airship))) return null;`).
Значит сессия использованного портала **не закрывается**. На следующем тике у этого портала
`haveSession == true`, но фаза уже не `CROSSED` → выполняется ветка `else` → `resetTrail`
стирает живой якорь **и** `break` пропускает все оставшиеся порталы. Этот тик не даёт
ни одного кандидата. Следующий тик стартует без якоря и работает как старый код.
Итог — чередование: перелёт раз в два тика.

**2. Якорь ставился не на ту сторону выходной плоскости.**

`entryTime` = `recent.towardTime()` = момент, когда развёрнутый AABB тела коснулся **полосы**
вокруг плоскости, а её полутолщина = `planeHalf + PORTAL_HYSTERESIS_DEPTH`, где
`planeHalf = max(from.aabbSupport(normal), to.aabbSupport(normal))`. То есть отображённая
поза крестится не в плоскости, а на `planeHalf + 0.1` **до** неё, и сдвиг на `+0.01` оставлял
якорь примерно на `planeHalf + 0.09` **позади** выходной рамки. Раньше это было не видно:
`settleExit` → `resetTrail` схлопывал след в тот же тик. Теперь якорь доживал до следующего
тика и уносил начало отрезка на исходную сторону выхода.

**3. `entryWithinExitSlab` структурно отказывал.**

`boundsAt(airship, t)` приводит нефинитный `t` к `0.0`, а `t = 0` теперь — сам якорь, который
по построению лежит внутри выставленной пластины. Проверка `latch.overlaps(...)` всегда
истинна → `continue` → отказ ровно тому пересечению, ради которого буфер и делался.

### Изменения

`PortalCrossingDetector.java`

1. **Убран `EXIT_ANCHOR_MAX_TICKS` и вся арифметика по тикам.** Жизненный цикл якоря теперь:
   выставлен перелётом → съеден ближайшим `captureTrail` → заменён следующим перелётом →
   удалён вместе со следом. Потерять его между перелётом и нужным ему свипом больше нельзя.
   `liveAnchor` — просто `EXIT_ANCHORS.get(id)`.
2. **`pruneTrails` удаляет якорь вместе со следом**, которому он принадлежит (замена бюджета
   тиков на реальный цикл жизни).
3. **`resetTrail` больше не уничтожает живой буфер** — при наличии якоря делает
   `reseedTrailFromExitAnchor`. Сброс существует, чтобы убить отрезок через шов; якорь —
   противоположное, это начало нового отрезка в кадре назначения.
4. **`armExitAnchor` ставит якорь абсолютно, а не сдвигом.** Две компоненты **в плоскости**
   берутся ровно такими, какими вышли (это и есть «относительно как sub-level выходит» —
   угол, центр или край; они приходят через собственный трансформ портала, поэтому рамка
   другого размера получает то же относительное место). Компонента **вдоль направления
   выхода** принудительно ставится в `0.01` от плоскости назначения
   (`exitFrame.mapPoint(portal.getOriginPos())`, `portal.getContentDirection()`). Ни ободка по
   граням, ни центра портала, и одинаково для любых размеров.
5. **`entryWithinExitSlab` измеряет пройденное расстояние от самого выхода.** Пластина
   по-прежнему отсекает вход «в нулевом расстоянии от выхода» (в т.ч. встречную грань той же
   рамки), но вход дальше по отрезку — это другой проём, и он допускается сразу, как бы близко
   порталы ни стояли.
6. Добавлен `hasBufferedExit(ServerSubLevel)` — предикат для контроллера.

`SableTransitController.java`

7. В ветке `else` при живом буфере — `continue` вместо `resetTrail` + `break`. Снятие сессии
   покинутого проёма ничего не говорит о проёме, в который тело влетает; отрезок уже начинается
   на выходной рамке и является ровно тем, с чем нужно сверять следующий портал. Перебор
   продолжается, обнаружение + перелёт + rehome остаются внутри одного тика.

- Ссылок на удалённые символы (`EXIT_ANCHOR_MAX_TICKS`, `anchor.tick`) не осталось.
- Баланс скобок: `PortalCrossingDetector.java` 106/106, `SableTransitController.java` 92/92.
- Сборка не запускалась (по требованию).

## 2026-08-15 (правка 3) — падение сквозь нижний портал: буфер жил не в том кадре и не в том тике

### Что говорит лог

Для `d90e5aa3` три rehome подряд:

| проход | destPos.y | Δ к предыдущему |
|---|---|---|
| 1 | −3662.939 | — |
| 2 | −3663.894 | **−0.954** |
| 3 | −3674.849 | **−10.955** |

Для `88374060` ровно та же форма: −0.810, затем −10.812.

Разница между вторым и третьим шагом = **−10.00** для обоих тел, то есть ровно высота лупа.
Второй проход корректный: тело улетело на один тик падения (~0.95) ниже. Третий проход —
это отображение **вниз на целый луп**, тело выбросило ниже нижнего портала. «Визуальный
отскок» — это и есть лишний флип, чей destPos почти совпадает с собственной позицией тела.

Значит ломается не количество тиков, а **выбор портала**: тело пересекает не следующий
портал, а **свою же выходную рамку**, и уезжает обратно вниз.

### Изъян 1 (главный, мой) — якорь проецировался по началу позы, а не по телу

В прошлой правке я ставил якорь «абсолютно»: считал расстояние от позы до плоскости выхода
и принудительно делал его равным 0.01.

Проблема в том, что `Pose3d.position()` — это образ локальной координаты плота `(0,0,0)`,
то есть **угол плота**, а не тело и не точка пересечения. `Frame` строит каждый блок как
`pose.transformPosition(block + 0.5)`. Прибив этот угол к плоскости, я сдвигал **весь объём**
вдоль нормали на столько, насколько угол случайно оказался далеко — это метры, а не 0.01.

Блоки в итоге оказывались заметно **позади** рамки, из которой только что вышли. Следующий
swipe видел честную картину «блоки были целиком на исходной стороне → стали за плоскостью»,
то есть классическое прямое пересечение **выходной рамки**, и rehome отправлял тело на
один луп **вниз**.

**Исправлено:** якорь снова строится как **относительный сдвиг** — берём позу, уже
пронесённую через портал (`StraddleMapping.mapPose`), и добавляем 0.01 вдоль
`getContentDirection()`. Само отображение уже несёт и положение, и поворот, и размер
выходной рамки, поэтому «относительно того, как sub-level выходит» и независимость от
размера порталов получаются бесплатно, без всякой проекции.

Заодно убран второй, source-кадровый экземпляр позы (`sourceEntry`): якорь теперь
выводится из **одной** позы через **одно** отображение. Именно два разных преобразования и
давали «буфер в своём собственном кадре», не совпадающий с сегментом, который он открывает.

### Изъян 2 — я ослабил единственную защиту выходной рамки

`armExitClearance` кладёт защёлку под UUID портала, **в который** тело влетело, а пластину
строит на прямоугольнике, **из которого** тело вылетело. Поэтому `withinExitClearance` для
портала, который реально стоит на выходной рамке, всегда отвечает «нет» — идентификаторы
не совпадают, ни для него, ни для его совпадающего двойника.

То есть `entryWithinExitSlab` — **единственная** проверка, закрывающая выходную рамку. В
прошлой правке я добавил в неё условие «отказывать только если вход ближе 0.01 к якорю», и
рамка осталась голой.

**Исправлено:** возвращена строгая форма `latch.overlaps(boundsAt(airship, entryTime))`.
Настоящий следующий портал это не задевает: его точка входа лежит на реальном расстоянии по
сегменту, вне пластины 0.01, и пропускается сразу.

### Изъян 3 — проверка «только что вышел» была мёртвым кодом

`hasBufferedExit` читал карту `EXIT_ANCHORS`. Но карту опустошает `captureTrail`, а он —
**первое**, что делает тик. Скан порталов, закрытие сессии и сброс следа идут **после**.
Значит во время скана карта всегда пуста, предикат всегда `false`, и контроллер по-прежнему
делал `resetTrail` + `break`. Вся прошлая правка «в один тик» фактически ничего не меняла.

**Исправлено:** факт переехал на сам сегмент — поле `Trail.seededFromExit`, которое ставится
в момент потребления буфера и живёт весь тик. `hasBufferedExit` читает его.

### Изъян 4 — сброс следа сносил выходной сегмент

`resetTrail` теперь просто **выходит**, если сегмент помечен `seededFromExit`: его начало и
есть та дверь, из которой тело вышло, — ровно та история, которую сброс уничтожал.

## 2026-08-15 (правка 4) — буфер стоял по центру лупа, а не на выходной рамке

**Наблюдение (оверлей `/iplsable_portal visualize_sweep_detector on`, низкий tick rate):**
«Прошлое» рисуется примерно по центру лупа, а не на 0.01 дальше выхода. Падение ~6 с.

**Что именно рисует оверлей.** `IplEnteringVolumeVisualization.captureTick` берёт
`PortalCrossingDetector.bufferedPose(ship)` → это `trail.older`, а `older` — это `trail.start`
предыдущего тика, то есть ровно якорь. Значит наблюдение прямо указывает на `trail.start`.

Найдено две причины, обе в файле `transit/PortalCrossingDetector.java`.

### Изъян A — доля времени бралась от ДРУГОГО отрезка (главная причина «по центру»)

Было, в `evaluate`:

```java
Double.isFinite(recent.towardTime()) ? recent.towardTime()
    : (Double.isFinite(sweep.towardTime()) ? sweep.towardTime() : Double.NaN)
```

`sweep = recent.mergePreferred(historic)`, а `historic` — это свип по отрезку `older → start`.
Его `towardTime` — доля **того** отрезка. Дальше `rebaseTrailThroughPortal` делает
`interpolate(trail.start, trail.end, crossingTime)`, то есть подставляет долю одного отрезка
в совершенно другой. В узком вертикальном лупе это и даёт точку где-то посередине лупа —
именно то, что видно в визуализации.

Стало: исторический хит выражается в текущей параметризации единственно правильным числом —
`0.0` (он произошёл на границе отрезка или раньше). `recent` по-прежнему используется как есть.

### Изъян B — `entryTime` — это касание ПОЛОСЫ, а не рамки

`sweepSegment` клипает отрезок по полосе `±(planeHalf + PORTAL_HYSTERESIS_DEPTH)` и берёт
`start = max(0, min(a, b))`. То есть `entryTime` — момент, когда блок только коснулся полосы,
а это почти целый support плюс гистерезис **не долетая** до плоскости. Поза с этого момента,
прогнанная через маппинг, оказывается почти на блок **до** выходной рамки, с входной стороны.
Прибавление 0.01 такую позу не спасает.

Стало: `armExitAnchor` больше не полагается на нормальную компоненту пришедшей позы. Он
измеряет тело ровно так же, как его меряет свип — центры блоков из базиса позы минус
`obbSupport` — находит **самую заднюю** точку тела вдоль `getContentDirection()` и сдвигает
позу целиком вдоль этого направления так, чтобы задняя точка встала ровно на
`EXIT_ANCHOR_OFFSET = 0.01` за плоскостью. Точка плоскости берётся как
`StraddleMapping.of(portal).mapPoint(portal.getOriginPos())`, то есть из собственного
маппинга портала.

Последствия, важные по существу:

* Две компоненты в плоскости не трогаются вообще → точка A остаётся там, где тело реально
  вышло, а не по центру портала.
* Точка плоскости приходит из маппинга портала → для рамок разного размера получается тот же
  относительный участок, без отдельной логики масштаба.
* Тело в точке A **целиком** за рамкой (задняя точка +0.01). Значит для выходного портала
  `fromPlane − support > 0`, и условие `enteredDestination` (`fromPlane + support < 0`) для него
  не выполнимо в принципе. Это структурно закрывает падение сквозь нижний портал: точка A
  больше не может прочитаться как свежее пересечение той двери, из которой тело только что
  вылетело.
* `Pose3d.position()` по-прежнему **не** используется как опорная точка: это образ

## 2026-08-16 (правка 5) — вылет из портала вместо телепорта + оверлей перестал врать

Луп живёт ~20 с (было 12.5 → 6 → 20). Оставалось два симптома: визуальный отскок на
выходе и «прошлое A», которое на оверлее ездит вниз до нижнего портала и возвращается наверх.

### 1. Оверлей показывал тело вместо точки A через тик

`IplEnteringVolumeVisualization.captureTick`:

```java
var buffered = PortalCrossingDetector.bufferedPose(ship);
replaceBufferAt(ship, buffered == null ? ship.lastPose() : buffered);
```

А `bufferedPose` было `trail.hasOlder ? trail.older : null`. На тике, когда трейл засеян из
буфера, `hasOlder` выставляется в `false` НАМЕРЕННО — прошлого нет, отрезок НАЧИНАЕТСЯ
у двери. Значит `bufferedPose` возвращал `null`, и оверлей рисовал `ship.lastPose()` — живое
падающее тело. Через тик он снова рисовал якорь. Отсюда и «опускалось до нижнего портала,
потом телепортировалось наверх», и медленное «всплытие/падение» на низком tick rate — это
биение между двумя чередующимися источниками картинки, ровно тот самый «эффект
совпадающих кадров». При этом сам детектор работал с правильным якорем.

Стало: живой якорь → `trail.older` → `trail.start` при `seededFromExit`. Фоллбэка на тело больше
нет ни в одной ветке. Метод отладочный, его единственный потребитель — оверлей, на логику
перехода правка не влияет.

### 2. На тике выхода тело сообщало НУЛЕВОЕ движение

`SableRehomeOps.executeHostedTransit`:

```java
pipeline.teleport(hosted, mappedPose.position(), mappedPose.orientation());
hosted.logicalPose().set(mappedPose);
hosted.updateLastPose();   // lastPose := logicalPose
```

`SubLevel.updateLastPose()` — это `this.lastPose.set(this.pose)`. То есть ровно в тот тик, когда тело
прошло самое большое расстояние, `lastPose == logicalPose`, и любой потребитель,
читающий движение как `lastPose -> logicalPose`, видит тело, которое НЕ ДВИГАЛОСЬ, но
сменило фрейм. Это и есть определение телепорта. Конкретно страдал
`IplStraddlePoseMap.leadPose`: при `length < 1e-9` он возвращает позу без упреждения, то есть
именно на тике выхода режущая плоскость отстаёт от тела.

Стало: сразу после `updateLastPose()` предыдущая точка ставится НА РАМКУ выхода — той же
самой точкой A. Вектор движения за этот тик становится ровно «плоскость портала →
конечная точка rehome», то есть тело НЕ появилось далеко от портала, а БЫСТРО ВЫЛЕТЕЛО.
Поза остаётся в destination-фрейме, поэтому исходная гарантия (ни одна source-space поза не
доживает до следующего тика) сохранена буквально.

Геометрия не дублируется: проекция вынесена из `armExitAnchor` в чистый
`PortalCrossingDetector.projectOntoExitPlane(airship, portal, destinationFramePose)`, который
ничего не сохраняет. `armExitAnchor` теперь = этот метод + запись в `EXIT_ANCHORS`. Точка A
одна и та же для детектора и для визуала.

Важно по порядку: ставится ДО `queueParentHandoff(...)`, чтобы handoff уехал уже с исправленной
предыдущей точкой, а не со схлопнутой. Майны проходят через тот же
`executeHostedTransit`, так что получают то же поведение без отдельного кода.

### 3. Новый аксессор (почему понадобился)

`SubLevel.lastPose()` возвращает только `Pose3dc` (чтение), а готовый
`client.IplSubLevelLastPoseAccessor` зарегистрирован в списке `client` → на выделенном
сервере его просто нет. Добавлен `ipl.sable.mixin.IplSubLevelPreviousPoseAccessor` с тем же
`@Accessor("lastPose")` и регистрацией в общем списке `mixins`. Клиентский аксессор НЕ тронут
и не перемещён — два accessor-интерфейса на одно поле допустимы, а перенос изменил бы то,
где он применяется.

### Что НЕ сделано и почему

Остаётся подозрение на редкий отскок в `IplParentDimSync.applyHandoff`: он маппит ВЕСЬ буфер
снапшотов интерполятора без фильтра по `gameTick()`. Если пакет движения за тик флипа
ляжет в буфер раньше handoff-RPC, то уже destination-поза будет отмаплена второй раз →
смещение на целый луп на один кадр. Это совпадает с «иногда». Не трогал: требует нового
поля в пейлоаде handoff и правки работающего слоя синхронизации, а без запуска игры это
гадание. Сначала стоит проверить, остался ли отскок после пункта 2.
