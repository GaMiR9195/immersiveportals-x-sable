## 1. Ободок постройки за порталом (п.1, вторая часть) — ИСПРАВЛЕНО ПО ИСТОЧНИКУ

**Факт из кода.** `SourceClipPortalFinder.findStraddlingPortalPlane` возвращала для
projection-прохода плоскость, сдвинутую наружу:

```java
Plane seamMatchedProjectionPlane = isUsingMatchingPortalClip(projectionPlane)
    ? projectionPlane.move(-FrontClipping.ADJUSTMENT) : projectionPlane;
```

`FrontClipping.ADJUSTMENT = 0.01` (проверено: `qouteall/imm_ptl/core/render/FrontClipping.java:28`),
`Plane.move(d)` = `new Plane(pos.add(normal.scale(d)), normal)`
(`qouteall/q_misc_util/my_util/Plane.java:34`).

Source-проход оставляет полупространство `n·(p−pos) ≥ 0` РОВНО на математической
плоскости портала. Projection-проход после `move(-0.01)` оставлял свою половину на
0.01 блока ЗА плоскостью. Значит слой толщиной 1 см попадал в ОБЕ оставленные
половины и рисовался ДВАЖДЫ — source-отрисовкой и mapped-проекцией. Этот
дважды-нарисованный слой и есть субпиксельный «ободок» по внешнему контуру
(на длинной палке 1×4 он заметнее всего: у неё почти весь силуэт — контур).

`ADJUSTMENT` — это z-fighting-защита IP для ЕГО СОБСТВЕННОГО прохода terrain'а
на destination-стороне. Terrain и sub-level — разная геометрия, поэтому наследование
этого сдвига никогда не закрывало щель между двумя половинами самого sub-level'а;
оно только создавало перекрытие внутри sub-level'а.

**Фикс:** обе половины режутся по одной и той же плоскости — точный стык без щели и
без перекрытия. Мёртвый после этого `isUsingMatchingPortalClip` и осиротевшие импорты
`FrontClipping` / `PortalRendering` удалены (не оставляю мёртвый код).

## 2. Неточный обрез физики за порталом (п.2) — ИСПРАВЛЕНО ПО ИСТОЧНИКУ

**Факт №1 — обрез шёл ПО ЦЕНТРАМ БЛОКОВ.** `IplStraddlePoseMap.buildKeepFilter`:

```java
return pos -> (pos.getX() + 0.5 - lp.x) * ln.x
            + (pos.getY() + 0.5 - lp.y) * ln.y
            + (pos.getZ() + 0.5 - lp.z) * ln.z >= keepThreshold;
```

Это `Predicate<BlockPos>` — блок оставался или выбрасывался ЦЕЛИКОМ по тому, с какой
стороны плоскости оказалась его середина. То есть обрез квантован ровно «по делениям
меша sub-level». На косом (45°) портале граница физики может уехать до полублока в
ЛЮБУЮ сторону от математической плоскости: где-то за порталом остаётся твёрдый
«кусман», где-то наоборот пропадает опора. Ошибка зависит от того, куда попал центр
конкретного блока, — поэтому она асимметрична поперёк проёма: слева material есть,
справа нет, ровно как в отчёте.

**Факт №2 — сверху накидывались ещё 0.9 блока.** `SEAM_SUPPORT_MARGIN = 0.9`
передавался в `getBlockCollisionKeepFilter`/`getSourceHalfKeepFilter` и через
`keepThreshold = -planeMargin` РАСШИРЯЛ оставленную половину на 0.9 блока ЗА
плоскость портала. Это ~блочная плита коллизии позади портала, живущая только в
выбранном для сущности кадре (`chooseCollisionFrame`) — то есть односторонняя.
Отсюда и «запрыгнуть можно», и «выталкивает с небольшим усилием будто коллайдер с
одной стороны».

**Фикс (источник, а не маска):**

1. `SEAM_SUPPORT_MARGIN` 0.9 → 0.0. Полупространство больше не раздувается за портал.
   Значение осталось системным свойством `ipl.sable.clip.seamSupportMargin`.
2. Тест по центру заменён на точный тест по РЕАЛЬНОМУ ОБЪЁМУ блока:

```java
double halfExtentAlongNormal = 0.5 * (Math.abs(ln.x) + Math.abs(ln.y) + Math.abs(ln.z));
... + halfExtentAlongNormal >= keepThreshold;
```

`0.5*(|nx|+|ny|+|nz|)` — опорная функция (support function) осевого единичного куба
вдоль plot-локальной нормали плоскости. Блок остаётся тогда и только тогда, когда
хоть какая-то его часть ещё лежит в оставляемой половине. Ничего, у чего есть
реальный материал на нужной стороне, больше не выбрасывается, и ничего целиком
залетевшего за плоскость не остаётся — при ЛЮБОЙ ориентации плоскости. Обрез больше
не привязан к решётке.

Правка одна и лежит в `buildKeepFilter`, поэтому её автоматически получают все четыре
потребителя фильтра — коллизия сущностей (`IplStraddleBlockClipMixin`), проверка
опоры (`IplStraddleCanFallMixin`), рейкаст/выделение (`IplProjectionAwareClipMixin`,
`IplStraddleOutlineMixin`). Расхождения между «что видно», «во что упираешься» и «что
выделяется» появиться не может.

### Остаточное ограничение (честно)

Полностью суб-блочный обрез (срез ПОСЕРЕДИНЕ блока под произвольным углом) в этом
контуре пока не представим: SAT-цикл Sable
(`SubLevelEntityCollision.collide`, строки 271–296) считает пересечение
сущность-OBB × коробка воксель-шейпа, а пересечение осевой коробки с наклонной
плоскостью — выпуклый многогранник, а не коробка. Чтобы резать буквально «как угодно»,
нужно вносить полупространство как дополнительную ось в SAT (или в нативный
rapier-контакт — там же, где ждёт заглушка `IplPortalRimManager`). Я это НЕ делал:
без компиляции и без прогона такой новый солвер был бы правкой по предположению.
Сделанное сейчас убирает квантование границы с 1 блока до 0 и убирает 0.9-блочную
плиту — то есть оба механизма, которые давали наблюдаемый «кусман».
